# AGENTS.md — supermortal.cn 文章写作规范

本文件用于指导 AI（以及作者本人）在看到写作需求时，按本博客统一的风格、结构与 frontmatter 规范生成文章。所有新文章都应先过一遍本规范。

## 博客定位

- 个人技术博客，读者是正在学习或准备动手的开发者/爱好者
- 内容以实战教程、踩坑记录、部署运维、AI 开发、服务器安全为主
- 价值点是“照着做就能复现”：每一步都给命令、配置、结果或截图
- 语气真诚、口语化但不拖沓，不写空话和营销腔

## 写作风格

1. **开头直给问题**：用一两句话说明“这篇文章解决什么”，不要大段寒暄
2. **叙事身份**：以作者第一人称“我”展开，允许记录真实踩坑过程，但最终要收敛到可复用结论
3. **结构清晰**：使用 `##` 分大节、`###` 分小节；步骤用有序/无序列表，关键命令用代码块
4. **每步可验证**：执行后给出预期输出、页面现象、检查命令或截图，方便读者确认
5. **适当总结**：结尾用简短“写在最后/小结”收尾，列出复盘点或下一步方向
6. **不堆术语**：首次出现的概念给一句人话解释，再进入具体操作
7. **截图配图**：关键界面/报错/成果用图片佐证；图片放文章同目录，正文用相对路径 `./01.png`
8. **常见问题**：长教程建议加 FAQ/常见报错小节，直接给解决方案
9. **开头给结论**：长文在标题后、展开细节前，先给一段能独立成文的一句话答案或摘要，方便检索和 AI 直接引用

## Markdown 规范

- 标题从 `##` 开始（`#` 只在文章正文首行使用一次，一般省略）
- 代码块必须标注语言，如 `bash`、`docker`、`markdown`、`python`
- 行内命令、文件名、环境变量用反引号包裹
- 强调少用加粗堆砌，最多对关键按钮/概念加粗
- 列表层级不超过两层
- 提示/警告使用 GitHub Admonitions：
  - `> [!NOTE]` 补充说明
  - `> [!TIP]` 操作建议
  - `> [!WARNING]` 风险提醒
  - `> [!CAUTION]` 高危险操作
- 外链不加 `target`，由主题统一处理；内部链接使用站内绝对路径 `/blog/...`

## 图片 alt 文本规范

### 基本要求

- **每张图必须有 alt**：不允许出现 `![](./01.png)` 这类空 alt；Markdown 代码块、表格里的语法示例占位（如 `![替代文字](URL)`）除外
- **alt 写"是什么 + 在干嘛"**，不要单纯描述图：先点明这张图属于哪个步骤 / 哪个界面，再写它展示的关键信息（菜单路径、按钮、配置值、对比对象）
- **同一张图被多次复用时按语境重写 alt**，不要复制粘贴：每处的 alt 应贴合所在小节语境，常用做法是先写一次最完整的，后续复用改成强调该步骤焦点的简化版
- **隐去敏感信息**：alt 与图本身都不要出现明文密钥、真实 Token、手机号、邮箱密码；如必须演示，用占位或马赛克

### SEO alt 三要素公式

每条 alt 尽量包含以下三类信息，缺一不可：

1. **主体（工具 / 品牌 / 产品名）**：截图里出现的具体技术栈，例如 宝塔、Docker、NapCat、AstrBot、Cloudflare、DNSPod、Astro、Vercel、fnOS、VMware、Python、BMAD 等
2. **场景 / 动作（界面 / 操作 / 对比 / 配置 / 步骤）**：截图处于哪个页面、做了什么操作，例如「容器列表」「设置弹窗」「WebUI 主页」「安装向导第 N 步」「版本对比表」「性能测评柱状图」「API 定价表」「配置文件字段」「终端输出」
3. **关键信息（参数 / 版本号 / 对象 / 状态）**：版本号（V4-Pro、v4.25.0）、参数（端口 23301 / 6199）、镜像名（soulter/astrbot）、路径（/AstrBot/data/cmd_config.json）、对象对比（V4-Pro vs V4-Flash）、状态（运行中、适配器已连接）

组合示例：

- `宝塔 Docker 容器列表` ← 主体+场景
- `NapCat WebUI Websocket Client 配置` ← 主体+场景
- `DeepSeek-V4 Pro 与 Flash 版本对比表` ← 对象+对比
- `硅基流动 Temperature 设置界面` ← 主体+界面
- `Cloudflare 控制台 supermortal.cn 流量统计概览` ← 主体+场景

反面示例（不要写）：「一张截图」「01」「02」「cloudflare」「腾讯云」「deepseek」——没有任何关键词，搜索引擎和读屏软件都抓不到信息。

## Frontmatter 规范

```yaml
---
title: '不超过 60 字的标题'
slug: '英文-kebab-case，如 deploy-openclaw-on-linux'
description: '不超过 160 字，说明文章要解决什么问题'
publishDate: 2026-09-06
tags:
  - 标签1
  - 标签2
language: '中文'
category: 教程
---
```

- `title`：准确、有行动指向（“部署 X”“学会 Y”“排查 Z”）
- `slug`：固定英文小写短横线格式，一旦发布不要随意修改，避免外链失效
- `description`：像搜索结果摘要，包含关键词和结果承诺
- `tags`：2~4 个；避免每个账号都用“教程”这类形式标签刷屏
- `category`：单值，一篇文章只归一个分类（可选，不填默认“未分类”）
- `language`：通常 `中文`

## 项目卡片视觉规范

- 项目数据统一维护在 `public/projects.json`，配图放在 `src/assets/projects/`
- 每个项目卡片都要配置 `image`（如 `deepseek-harness-guide.png`、`bot-deploy.png`），卡片右侧会用渐隐方式展示配图；纯文字卡片会破坏首页和项目页的视觉一致性
- 卡片配图建议 800x500 左右的界面截图或终端卡片，右侧信息密度高、有明确主题色，风格对齐 DeepSeek Harness Guide 与 Bot Deploy 两张现有配图
- 终端风格配图可用 `node scripts/generate-project-card-image.mjs` 重新生成；新增项目时参照该脚本生成同风格配图
- 链接图标映射：`site` 用链链接图标，`github` 用 GitHub 图标，`doc` 用文档图标，`release` 用包图标；新增类型时同步更新 `src/components/projects/ProjectSection.astro`

## 写作流程建议（给 AI）

1. 先确认主题属于博客领域（教程/运维/AI/项目/踩坑），不符合则先说明
2. 列出大纲：背景 → 前置准备 → 分步骤实操 → 验证结果 → 常见问题/总结
3. 写作时保持信息密度，代码与截图必须有实际来源，禁止编造命令输出
4. 完成后自检：frontmatter 是否齐全、步骤是否可复现、代码块语言是否正确、图片路径是否存在
5. 涉及外部服务/版本号时注明日期和环境，避免过期信息误导

## 禁止事项

- 禁止编造不存在的命令输出、报错或截图
- 禁止把搜索到的二手结论当成自己验证过的结果
- 禁止发布未验证的“最佳实践”或安全建议（尤其涉及删除、格式化、生产环境）
- 禁止在正文加入“本文由 AI 生成”“仅供参考”等影响专业感的文案
- 禁止出现未定义的连接词堆砌（“综上所述/众所周知”），保持直接
